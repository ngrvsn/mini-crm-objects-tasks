# Аудит безопасности

Проверено 5 ноября 2026 года на локальной Supabase, production-сборке приложения и облачном проекте через читающие запросы. Проверки запускаются повторно в GitHub Actions для каждого изменения кода.

## Доступ к данным

- RLS включена на `profiles`, `objects`, `tasks` и `task_status_history`. Исполнитель читает только назначенные задачи, связанные с ними объекты и их историю; постановщик читает активные записи целиком.
- Ролям браузера не выданы прямые права на запись в таблицы. Функции записи проверяют роль и пользователя на стороне PostgreSQL. Переход статуса и добавление записи истории происходят в одной транзакции.
- Проверены прямые запросы в обход интерфейса: чтение чужих строк и истории, повышение своей роли, запись в таблицы, запрещённые переходы, пустой комментарий при возврате и смена статуса принятой задачи. Запросы отклоняются.
- Логическое удаление скрывает объект или задачу от клиентских запросов и сохраняет историю в БД.
- Создание и перенос задачи блокируют строку целевого объекта до конца транзакции. Конкурентные тесты подтверждают, что одновременное удаление объекта не оставляет активную задачу под удалённым объектом.

## Сессия и веб-приложение

- В браузере access token хранится только в памяти. Refresh token выдаётся в HttpOnly cookie с `SameSite=Strict`; production cookie также получает `Secure`. На выходе сервер отзывает refresh-сессию и очищает cookie.
- Маршруты входа, обновления и выхода отклоняют запросы с чужим `Origin`. Ответы с токеном не кэшируются. Страницы запрещают встраивание в iframe через `frame-ancestors 'none'` и `X-Frame-Options: DENY` и отправляют `X-Content-Type-Options: nosniff`.
- Проверены восстановление после перезагрузки, синхронизация двух вкладок и задержанные ответы профиля и refresh. Устаревший ответ не должен возвращать пользователя в систему или стирать токен нового входа. В браузерах с Web Locks выход и refresh выполняются последовательно; тест с задержанным ответом подтверждает отсутствие cookie после завершённого выхода.
- Новый вход отменяет ожидающий refresh и выполняется под тем же Web Lock. Тесты с задержанными ответами `401` и `200` проверяют, что старый запрос не сбрасывает новую сессию и не подменяет её refresh cookie после перезагрузки. Повтор Axios-запроса с `401` разрешён только в той же сессии, в которой запрос начался; при смене пользователя в другой вкладке прежние данные сразу скрываются.
- В отслеживаемых файлах и истории Git не обнаружены строки вида `sb_secret_...`, строка подключения с паролем или JWT-подобный ключ. Локальные `.env*`, кроме шаблона, исключены из Git.

## Облачный стенд

Читающая проверка подтвердила вход одного постановщика и двух исполнителей, назначенные роли и ограничения видимости задач, объектов и истории. Постановщик видит 3 объекта и 4 задачи; каждый исполнитель видит только 2 назначенные ему задачи. `GET /auth/v1/settings` вернул `disable_signup: true`. Прямые `PATCH` задачи и `DELETE` истории на несуществующем UUID вернули 403 для обеих ролей.

Вторая миграция применена без сброса базы. После неё в облаке остались 3 активных объекта и 4 активные задачи, активных задач под удалённым объектом нет. Функции создания и переноса задачи используют блокировку строки объекта; вызов создания доступен роли `authenticated` и недоступен `anon`.

Дополнительно Playwright прошёл вход и выход всех трёх пользователей через локальный Next.js, подключённый к облачной Supabase. Проверены списки, карточки и история; чужая задача в интерфейсе исполнителя не открылась. Эти проверки не меняли данные облачной базы.

## Воспроизведение

После `pnpm exec supabase start` и `pnpm seed:local`:

```text
pnpm db:test         # 12 проверок PostgreSQL/RLS
pnpm test:security   # прямые HTTP-запросы к Data API
pnpm test:concurrency # создание/перенос задачи одновременно с удалением объекта
pnpm test:e2e        # роли, экраны, история, сессия и полный цикл задач
pnpm audit           # известные уязвимости зависимостей
pnpm build           # production-сборка
node scripts/health-smoke.mjs  # готовый сервер, Supabase и защитные заголовки
```

GitHub Actions дополнительно выполняет линтер, типы, unit-тесты, сборки на Node 20 и 22 и заключительный healthcheck.

## Проверка после получения сервера

Проверить HTTPS, настройки прокси и домена, `APP_ORIGIN`, флаг `Secure` у cookie, внешний `/api/health` и пользовательские сценарии по публичной ссылке. Уже выпущенный access JWT может работать до своего срока истечения; выход отзывает refresh-сессию и удаляет токен из памяти приложения.
